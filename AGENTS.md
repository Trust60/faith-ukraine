# Faith Ukraine — интернет-магазин японской косметики

Премиальный e-commerce профессиональной/японской косметики. Каталог без онлайн-оплаты:
контент-модель и админка на Payload, корзина — собственная (Zustand).

## Философия кода

- **Keep it simple.** Всегда предпочитаем простые, читаемые решения сложным.
- **Код лёгкий и читаемый.** Не усложняем реализацию.
- **Без лишних абстракций.** Пишем прямолинейный код, который легко понять.
- **Никаких «костылей».** Не лепим хаки-заплатки, которые потом тяжело поддерживать.
- **Долговечные решения** с понятным потоком данных и низкой связанностью (low coupling).
- Избегаем лишних цепочек условий, дублирования логики и скрытых сайд-эффектов.
- Если корректное решение требует большего объёма — объясняю компромисс и спрашиваю
  владельца, а не выкатываю хрупкую заплатку.

## Структура проекта

Весь код — в `src/`. Алиасы импортов заданы в `tsconfig.json`.

| Каталог                    | Назначение                                       |
| -------------------------- | ------------------------------------------------ |
| `src/app/`                 | Страницы и лейауты App Router                     |
| `src/components/ui/`       | Базовые UI-примитивы (кнопки, инпуты, иконки)      |
| `src/components/layout/`   | Лейаут-компоненты (Header, Footer, навигация)      |
| `src/components/elements/` | Компоненты с бизнес-логикой                        |

| `src/utils/`               | Утилиты по категориям (`cn.ts`, `format.ts` …)     |

**Алиасы путей** (`tsconfig.json`):

- `@/*` → `src/` (корень)
- `@/layout/*` → `src/components/layout/`
- `@/ui/*` → `src/components/ui/`

Импортируем короткими алиасами (`@/ui/IconButton`, `@/layout/header/Header`,
`@/utils/cn`), а не относительными цепочками `../../`.

## Архитектура и работа с данными

- **Full-stack Next.js + Supabase.** Серверные операции — в Server Components / Route
  Handlers / Server Actions согласно гайдам в `node_modules/next/dist/docs/`.
- **Аутентификация — только Payload.** Supabase Auth НЕ используем.
- **Подключение к БД — через connection pooler** (Supavisor / pgBouncer), не прямое.
  На serverless (Vercel) прямые коннекты быстро упираются в лимит.
- **SQL не выполняю сам.** Любые миграции / SQL-запросы я отдаю текстом — их
  выполняет владелец проекта вручную в Supabase.
- **Картинки товаров** хранятся в Supabase Storage, не в репозитории.

## UI/UX — фундаментальные правила

- **Адаптивность first.** Все экраны работают на мобильных и десктопе. Mobile-first,
  брейкпоинты Tailwind; проверяем тач-таргеты (≥ 44px) и читаемость.
- **Accessibility — обязательна.**
  - Семантический HTML: `<header>`, `<nav>`, `<main>`, `<section>`, `<article>`,
    `<aside>`, `<footer>`, `<ul>/<ol>/<li>`, `<button>`, `<a>`, `<label>`,
    `<figure>/<figcaption>` и т.п. вместо «дивных» обёрток.
  - Иерархия заголовков `h1 → h2 → h3` без пропуска уровней.
  - `alt` у изображений, `label` у полей форм; видимые фокус-индикаторы и полная
    навигация с клавиатуры (логичный tab-порядок).
  - Контраст текста по WCAG AA; совместимость со скринридерами.
  - Декоративным SVG-иконкам ставим `aria-hidden="true"` (и `role="presentation"`),
    чтобы скринридер их не озвучивал.
  - `aria-*` — только где не хватает семантики (`aria-label`, `aria-expanded`,
    `aria-disabled` …).
- **Отзывчивость и дружелюбность.** Состояния `loading` / `empty` / `error` /
  `success` у каждого асинхронного блока. Понятные сообщения об ошибках форм.
- **Консистентность.** Переиспользуем компоненты (shadcn/ui + общие UI-примитивы),
  единые отступы, типографика и радиусы.

## Производительность

- Приложение должно быть **быстрым и оптимизированным**. Используем серверный рендер,
  стриминг, ленивую загрузку и `next/image` для фото товаров.
- **Анимации только оптимизированные.** Анимируем `transform` и `opacity` —
  то, что браузер композитит на GPU. НЕ анимируем свойства, вызывающие layout
  (`width`, `height`, `top`, `left`) или repaint (`color`, `background`,
  `box-shadow`). Для простых анимаций предпочитаем CSS-переходы. `will-change`
  используем точечно и снимаем после анимации.
- **Framer Motion.** Используем компонент `<m>` вместо `<motion>` (меньше бандл),
  с уважением к `prefers-reduced-motion`.
- **Без антипаттернов.** Не тащим лишние зависимости, не делаем prop-drilling вместо
  Zustand, не дублируем логику, не блокируем рендер тяжёлыми вычислениями на клиенте.

## Организация кода

- **Один файл — максимум 100–150 строк.** Всё что больше — рефакторим и раскладываем
  по отдельным файлам (компонент / хук / утилита / типы / запрос разделены).
- Один компонент = одна ответственность. Бизнес-логику выносим из JSX в хуки/утилиты.
- **Циклы и списки — без инлайна.** В `.map()` рендерим вынесенный компонент
  (`<NavLink ... />`), а не собираем разметку и логику ребёнка прямо в цикле. Сложную
  логику внутри цикла выносим в именованную функцию, условный рендер компонентов — в
  отдельный компонент. Тонкий семантический враппер (`<li>` вокруг вынесенного
  компонента) — это нормально; избегаем именно инлайна разметки/логики в теле цикла.
- Имена и стиль кода — как в окружающем коде; следуем ESLint + Prettier.
- **Классы только через `cn`.** Любую склейку `className` (условные классы, проброшенный
  `className`, объединение базовых стилей с вариантами) делаем хелпером `cn` из
  `src/utils/cn.ts` — это `clsx` (условия/массивы) + `tailwind-merge` (разрешение
  конфликтов Tailwind-классов). НЕ собираем классы шаблонными строками
  (`` `base ${x}` ``) или конкатенацией — иначе конфликтующие утилиты не схлопываются.

## Конвенции кода

### TypeScript

- Strict-режим (`"strict": true` в `tsconfig.json`).
- Интерфейсы — с префиксом `I` (`IButton`, `ITokenInside`).
- Type-алиасы — с префиксом `T` (`TUserDataState`). Типы пропсов компонента — тоже
  с `T`: `T` + имя компонента + `Props` (`TIconButtonProps`); деструктурируем пропсы
  прямо в параметрах функции.
- Импорт типов — явный: `import type { FC } from "react"`.
- Варианты — через union-типы (`'primary' | 'link' | 'outline'`).
- Вместо TS-`enum` — объект `as const` + производный тип:

```typescript
export const PaymentStepEnum = {
  PaymentSelection: "PaymentSelection",
  PromoCode: "PromoCode",
} as const;

export type PaymentStepEnum =
  (typeof PaymentStepEnum)[keyof typeof PaymentStepEnum];
```

### Компоненты React

- Деструктуризация пропсов прямо в параметрах функции: `({ ... }: TButtonProps)`.
- Бизнес-логику выносим в кастомные хуки (`src/hooks/`).
- Клиентские компоненты — с директивой `"use client"` в начале файла.

### Экспорты

- **Named exports** для всех компонентов, утилит и функций.
- **Default export** — ТОЛЬКО для роут-компонентов Next.js (`page.tsx`,
  `layout.tsx`, `not-found.tsx`).
- Barrel-экспорты (`index.ts`) для чистых импортов.

### Именование

- `PascalCase` — компоненты и типы.
- `camelCase` — переменные, функции, пропсы.
- `ALL_CAPS` — константы и вычисляемые значения.
- Функции называем описательно (`transformUserToState`, `generateSlug`) и по
  действию (`setIsLoggedIn`, `onClickLink`).
- **Имена файлов:** компоненты — `PascalCase.tsx` (`IconButton.tsx`, `NavLink.tsx`);
  остальные файлы (утилиты, хуки, сторы, конфиги, типы) — строчные / kebab-case
  (`cn.ts`, `nav-config.ts`). Исключение — роут-файлы Next.js по конвенции фреймворка
  (`page.tsx`, `layout.tsx`, `not-found.tsx`).
